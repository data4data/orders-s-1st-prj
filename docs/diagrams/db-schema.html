Database schema

One shared MySQL 8 database for every MyOil's store. Blue tables carry a store_id and are scoped automatically by the Doctrine TenantFilter; grey tables belong to the platform. Planned design, not generated from migrations yet.

Reading the lines

  • 1:n: one parent, many children
  • n:m: many-to-many through a join table
  • Dashed line: optional (nullable FK) or logical link
  • Thick arrows between groups name the table-level link they stand for.
  • The detail tabs use crow's-foot notation with full columns.

Key choices

  • The cart is a draft order, so there are no separate cart tables.
  • Customers belong to one store. The same email can register in several stores.
  • Staff are global and get access to stores through store_membership.
  • VAT is platform-wide, per country and category, with validity dates. The store's country decides the rate.
  • Several stores per country are allowed. The demo has three MyOil's shops in NL.
  • Each store has its own branding (name, logo, colours) plus its own low-stock threshold.

Tenant resolution

  • Each request's Host header is looked up in store_domain.host. An unknown host returns 404 (fail closed).
  • A store can have several hosts, such as myoils-auto.shop.test and later myoils-auto.nl. One of them is the primary.
  • The admin runs at admin.shop.test and takes the store from the store switcher kept in the session.

Access

  • store_membership.role maps to Symfony roles for the selected store only.
  • is_super_admin may pick "All stores", which disables the filter explicitly (read-only by default).

VAT over time

  • The rate is chosen by (store.country_code, product.tax_category, order date).
  • Rates are stored as DECIMAL(5,2), for example 21.00 or 5.50. The domain reads them as exact decimal strings, never as floats.
  • Past orders keep their own snapshot and never re-read this table.
Order numbers come from store_sequence with SELECT … FOR UPDATE. This gives gap-tolerant, per-store numbers such as AUTO-000123.

Catalog

Lubricant products (engine, industrial and agricultural oils, greases). A product is sold as package-size variants (1 L, 5 L, 20 L, 60 L, 208 L drum). Technical specs such as SAE viscosity, ISO VG, API/ACEA and OEM approvals are filterable attributes.

Inventory

  • The number that can be sold is on_hand − reserved. A DB check enforces reserved ≤ on_hand.
  • checkout (→ payment_pending): reserved += qty
  • pay (→ paid): on_hand −= qty, reserved −= qty
  • cancel before payment: reserved −= qty
  • The rules live in the pure Domain\Inventory policy. The version column prevents lost updates.

Prices

  • Prices are entered net in minor units, in the store currency.
  • Gross is calculated as net × (1 + rate) by Domain\Pricing. It is never stored on the catalog.

Specs & documents

  • Attributes are per store and drive the PrimeVue catalog filters.
  • product_category is a plain join table. It is protected through its parents, which are both tenant-filtered.
  • Safety data sheets (SDS) and technical data sheets (TDS) are attached as product_document (an https address for now; uploads later).
  • Images are links (https:// URLs) in product_image. A row with a product_variant_id shows only for that pack size.

Customers, orders & payments

The order doubles as the cart while in draft. At checkout it gets a number, and prices, VAT and addresses are snapshotted, so later catalog or tax changes never alter it.

Money

  • Every amount is an integer in minor units of orders.currency_code. Domain code wraps it in the Money value object.
  • total_gross = total_net + total_tax. The domain rounds per line, then sums.

Address rules

  • One address row can serve both roles (usable_for_billing + usable_for_shipping). "Delivery same as billing" means one row with both flags.
  • A registered customer always has at least one billing and one delivery address. Both are required at registration, and deleting the last one of either kind is blocked.
  • Guests have no address book. They enter addresses at checkout and those go straight into the order snapshot.
  • B2B: company + vat_id are captured now. Reverse charge comes later through TaxRateResolverInterface.

Snapshots

  • Order lines copy SKU, names, net price and VAT rate at checkout.
  • Addresses are Doctrine embeddables stored as billing_* and shipping_* columns.
  • Guest checkout: customer_id is NULL and customer_email is required.

Payments

  • An order can have several payment attempts. One captured payment covering total_gross allows the order to move to pay.
  • Webhooks are stored first and deduplicated by (gateway_code, external_event_id), then processed asynchronously.

Why the name orders?

  • order is a reserved word in SQL.

Conventions

Rules that apply to every table, so new tables fit in without special cases.

TopicRuleWhy
Primary keysINT UNSIGNED AUTO_INCREMENTSmall, fast InnoDB indexes.
Public identifierspublic_id BINARY(16) UUID v7 on store, product, variant, customer, orders, paymentNothing guessable in URLs or API payloads. UUID v7 is time-ordered, so indexes stay compact.
Tenant columnstore_id INT NOT NULL with an FK to store. Composite indexes start with store_id.Every filtered query hits an index prefix.
UniquenessBusiness keys are unique per store: (store_id, sku), (store_id, slug), (store_id, email), (store_id, order_number)Stores are independent namespaces.
Money & ratesAmounts: INT minor units (cents). VAT and percentage rates: DECIMAL(5,2).No floating-point errors. Rates are exact decimals; each line is rounded half-up to cents.
SnapshotsOrders copy the prices, VAT, names and addresses they depend on.History stays correct when the catalog or tax rates change.
Concurrencyversion column (Doctrine optimistic lock) on product, product_variant and ordersPrevents overselling and double transitions.
TimeDATETIME stored in UTC as datetime_immutableConsistent across stores in different time zones.
EnumsVARCHAR mapped to PHP backed enumsNew values need no ALTER TABLE.
Framework tablesmessenger_messages, doctrine_migration_versionsPlatform-level, not shown in the diagrams.
