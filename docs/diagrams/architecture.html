Architecture

A multi-store lubricant shop on Symfony 7.4. One shared database, a pure-PHP domain core, Symfony Workflow state machines, pluggable payment gateways, and two separate frontend stacks: Bootstrap + jQuery, and Vue 3 + PrimeVue + Tailwind. See architecture.md in the repository root for the written summary.

What each layer may use

  • Domain: plain PHP only. It holds calculators, policies and value objects, is fully unit-testable, and has no I/O.
  • Entity: Doctrine entities in src/Entity, the Symfony standard. They may use Domain value objects only.
  • Application: Domain, entities and ports. Handlers are thin: load, call the domain, apply the transition, persist.
  • Infrastructure: implements ports and holds Doctrine, Workflow, gateways and tenancy.
  • UI: turns HTTP or CLI input into a command DTO and dispatches it on the bus. It contains no business rules.

Why entities have their own layer

  • We chose Doctrine attribute entities for pragmatism. Only the rules are pure.
  • src/Entity is where Symfony, its docs and make:entity expect them. deptrac treats it as a separate layer that Application and Infrastructure may use, and that may use only Domain.
  • Entities turn their integer columns into Money and other Domain value objects in their getters.

How a request is scoped to one store

The store is resolved from the host before the firewall runs, so even loading the logged-in customer is already scoped. With no resolved store, tenant queries return nothing (fail closed).

Building blocks

  • TenantAwareInterface: a marker on every entity that has store_id.
  • TenantFilter extends SQLFilter adds alias.store_id = :storeId to queries on those entities. Without a parameter it returns 1 = 0.
  • TenantAssignListener (Doctrine prePersist) sets the store and throws if there is none.
  • TenantContext::runAsPlatform(fn) disables the filter explicitly for fixtures, CLI and the super-admin.

CLI & async

  • Console commands take a --store=myoils-auto option.
  • Messenger messages carry a StoreStamp. A middleware restores the tenant before the handler runs.
A test suite (TenantIsolationTest) seeds two stores and checks that each repository cannot see the other store's rows.

Where the rules live

  • Guards are workflow.order.guard.<transition> listeners. They only ask pure Domain policies, such as StockPolicy::canReserve(), and call $event->setBlocked(true, reason).
  • State changes that have effects (reserving or deducting stock, snapshotting prices, the order number) are done by the handler in the same DB transaction as $workflow->apply().
  • Side effects such as the audit row (order_status_history) and emails are handled in completed listeners. Emails go through async Messenger.

Stock effects

  • checkout: reserve
  • pay: deduct (reserved → sold)
  • cancel before pay: release
  • cancel after pay: restock
  • refund after shipping: restock only when goods come back (returns are a later phase)
Rule: before the order ships, the shop cancels it (the handler issues the full refund through the gateway first). After it ships, money goes back through refund, mainly after delivery.

A separate workflow on Payment::$state. Payment events drive order transitions. The order never inspects gateway specifics.

Linking payment → order

  • payment.completed.capture → dispatch ApplyOrderTransition(pay)
  • payment.completed.refund → the order completes cancel (not yet shipped) or refund (shipped or delivered)
  • payment.completed.fail → the order stays payment_pending, and the customer can retry with a new payment attempt

Partial refunds

  • Recorded as payment_refund rows. The payment moves to refunded only when fully refunded.

Thin boundaries

  • Controllers are about 10 lines each: validate the DTO and dispatch.
  • Handlers coordinate the work. The domain calculates and decides.
  • The workflow decides whether a change is allowed. The handler decides what changes.

Safety

  • Optimistic lock (version) on the order and the variants.
  • Webhooks are deduplicated by (gateway_code, external_event_id).
  • A scheduled job cancels payment_pending orders after a TTL and releases their stock.

How switching works

  • #[AutoconfigureTag('app.payment_gateway')] on the interface.
  • The registry receives a #[AutowireLocator] indexed by code().
  • store.payment_gateway_code chooses the gateway per store. Credentials come from env vars per gateway.

Where they live

  • Payment port: Application\Payment. Adapters: Infrastructure\Payment.
  • Discount, shipping and tax interfaces and their pure implementations: Domain\*. They are wired through Symfony tags in config/services.yaml.

Base classes

  • AbstractPaymentGateway holds shared signature checking and money conversion.
  • AbstractApiController holds shared JSON, validation and CSRF handling.
  • The frontend has matching base layouts: bootstrap/base and vue/base.

Isolation rules

  • Templates extend bootstrap/base or vue/base, never both. There is no shared global CSS.
  • Tailwind 4 uses @import "tailwindcss" source(none) with @source limited to assets/vue and templates/vue. It never scans Bootstrap templates.
  • Tailwind's preflight reset exists only in the Vue bundles. Bootstrap's reboot exists only in the Bootstrap bundle.
  • Shared design tokens (spacing, fonts, radii) come from one tokens.json, compiled into SCSS variables and Tailwind @theme. The tokens are shared, the CSS is not.

Per-store branding

  • Each store sets its logo_url, favicon_url, primary_color and accent_color.
  • Both base layouts print them as CSS variables (--brand-primary, --brand-accent + generated shades) in a small inline <style>.
  • Bootstrap maps them to --bs-primary. Tailwind @theme maps them to primary-*. PrimeVue Aura receives them at runtime through updatePrimaryPalette().
  • The admin keeps a neutral platform theme and shows only the store logo in the switcher.

Vue mounting

  • Storefront: Twig renders <div data-vue-page="Catalog" data-props='…'>, and storefront.js mounts the matching page component.
  • Admin: one Twig shell route /{any} on admin.shop.test. Vue Router takes over from there.
  • API calls go through a typed ApiClient interface with the session cookie and the X-CSRF-Token header.

Branching strategy

There are three long-lived branches, one per environment. Changes only flow upward: feature/* → test → stage → production. Hotfixes start from production and are merged back down.

Branches

  • test is the default branch. Feature pull requests target it, and CI runs unit, integration, deptrac, PHPStan and linting.
  • stage: pre-production. It is deployed to the staging environment for final QA with fixtures or anonymised data.
  • production: live. It only receives merges from stage or hotfix/*, and every release is tagged with SemVer.

Protection

  • No direct pushes to any of the three branches. Pull requests need green CI and one review.
  • Merges from stage to production are restricted to maintainers.
